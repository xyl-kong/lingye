4. 根源：为什么同一类问题会反复出现

① 设计基准漂移

先按截图近似实现，后来核对 BlockSuite/AFFiNE 源码才发现结构、尺寸、状态不同，只能重排。最早还有一次整体方向反转：v0.8 的紫蓝悬浮圆角/柔光 → 10-30 的白色平直/贴边窄侧栏，壳层、输入框、底栏全部跟着改。

  • 对策：开工前锁定官方 commit/截图与 token 表
  • 对策：先定视觉方向，再大量实现；变更需记录

② 组件化滞后

菜单、工具条、设置行、颜色入口先各处手写，视觉/行为不一致后再抽组件，迁移成本高。

  • 对策：同类 UI 出现第 2 次就抽组件
  • 对策：MenuRow / SettingsRow / ParameterBar 先行

③ Compose 状态建模错误

页面对象原地修改、可变引用被强跳过，导致“＋”不跟随、编辑器残留、列表不刷新；表面像 UI bug，实际是状态观察问题。

  • 对策：UI 状态用不可变值类型/快照
  • 对策：显式 geometryRevision / key，禁止依赖引用变化

④ 响应式未作为验收维度

宽屏通过就发布，640dp、360dp、200% 字体、分屏才暴露折行和裁切，随后补布局。

  • 对策：定义 360/540/640/1280dp + 200% 字体矩阵
  • 对策：每个界面至少在 2 个宽度截图验收

⑤ 桌面交互直接照搬

官方依赖悬停、右键、滑出菜单；平板触控没有这些路径，只能改成常驻工具条/长按/更多菜单，交互反复调整。

  • 对策：先做“桌面→平板”交互映射表
  • 对策：把不可用入口隐藏或禁用，不伪装

⑥ 数据格式演进缺少一次性设计

格式 23/24/25 逐项追加，Journal/模板元数据起初不在备份内，后来补 metadata.dat，迁移与兼容测试反复增加。

  • 对策：格式变更走版本化 ADR + round-trip 测试
  • 对策：元数据从第一天就纳入备份

⑦ 构建与验证流程不稳

构建副本用 `/E` 同步留下旧根包类；中文路径、Gboard 覆盖、硬编码坐标导致验证结果失真。

  • 对策：源码副本必须 `/MIR`；搬包后 clean build
  • 对策：点击用 uiautomator bounds，不硬编码坐标

⑧ 没有视觉/性能回归门禁

UI 靠人工截图对比，性能靠临时采样；没有基线就无法判断“改好了”还是“看起来差不多”。

  • 对策：关键界面建立截图基线（3 个宽度）
  • 对策：性能改动必须同条件前后采样

6. 可执行的规避规则

基准先行

每个界面先写清“对照哪个官方 commit/截图、哪些尺寸、哪些状态”，再写代码；基准变化单独记录，不边写边换参考。

第二次就抽象

同类菜单/设置行/参数条/颜色入口出现第二次时立即抽组件，禁止复制第三份。

状态不可变化

UI 只读不可变模型；几何/内容用值类型和 revision 驱动；不使用可变对象引用作为重组依据。

响应式是完成标准

每个界面至少在 1280dp、640dp、360dp 与 200% 字体下截图；不通过不算完成。

交互映射表

官方悬停→长按/提示、右键→更多菜单、滑出菜单→参数条；无法映射的入口隐藏或禁用。

格式变更走 ADR

页面/备份格式变更先写迁移与回滚方案，补 round-trip 测试；元数据与图片引用从一开始就纳入备份。

构建卫生

源码副本 `/MIR`；搬包/删文件后 clean build；发布前核对 APK 哈希、版本、测试数与文档一致。

验证可复现

点击用 uiautomator bounds；截图命名并归档；模拟器输入先收键盘；不把模拟器帧率当性能结论。

视觉/性能门禁

关键界面建截图基线；性能改动同条件前后采样；没有基线就不声明提升。
